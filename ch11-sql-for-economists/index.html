1  •  You Already Know This

Six operations, ten chapters of practice, and a new spelling.

SQL and pandas Share an Ancestor

You have spent ten chapters filtering rows, selecting columns, grouping, aggregating, sorting and merging. Those six operations are essentially all of SQL.

In 1970 Edgar Codd proposed organising data into relations — tables — manipulated by a small formal algebra. SQL was built directly on it. Pandas came four decades later and borrowed the same operations.

pandas is procedural

You give the steps. Filter, then group, then take the mean. Each step makes an object you could inspect. A recipe.

SQL is declarative

You describe the table you want. The engine decides how to make it — often in a different order than you wrote, chosen for speed.

You are learning notation, not concepts. That is why this takes days rather than months.

The Order You Write It Is Not the Order It Runs

FROM runs first — you cannot filter a table you have not named.

WHERE runs before GROUP BY. So WHERE cannot reference an average — at the moment it runs, no averages exist yet.

That is what HAVING is for. “WHERE vs HAVING” is the most common entry-level SQL interview question there is, and the answer has nothing to do with which one is better.

They run at different times.

Both Clauses, Doing Different Work

Which categories earned more than \$10,000 since December 2025?

SELECT category, SUM(revenue) AS rev
FROM sales
WHERE  month >= '2025-12'
GROUP BY category
HAVING SUM(revenue) > 10000
ORDER BY category
category |   rev
---------+---------
books    | 12000.0
coffee   | 13000.0

WHERE removes November before any summing. Without it, books total \$16,000 and the answer covers the wrong period with no warning.

HAVING drops tools (\$3,500) after grouping — which WHERE could not do, because at that point no total existed.

Try to Collapse Them and the Database Tells You

duckdb.sql("SELECT category, SUM(revenue) FROM sales "
           "WHERE SUM(revenue) > 10000 GROUP BY category")
BinderException: Binder Error:
WHERE clause cannot contain aggregates!

That error message is the execution-order table restated. It is also, almost verbatim, the answer to the most common entry-level SQL interview question there is.

Poll: Why Can't WHERE See an Average?

SELECT dept, AVG(pay) FROM staff
WHERE AVG(pay) > 50000 GROUP BY dept   -- BinderException

Why does this fail?

A) AVG is misspelled — SQL wants MEAN
B) WHERE runs before GROUP BY, so no average exists yet
C) You can never filter on an average in SQL
D) WHERE needs the column listed in SELECT first

Answer: B — It Is a Question of Timing

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. When WHERE runs, the rows have not been grouped, so there is nothing to average. Move the condition to HAVING and it works.

Why C is the tempting wrong answer: you absolutely can filter on an average. You just have to do it after the aggregation exists — which is the entire job description of HAVING.

First: Where Is the Database?

There isn't one.

duckdb.sql("SELECT ... FROM customers") reads the name customers out of your Python namespace — the same variable you built one line ago with pd.DataFrame(...) — and runs the query against that DataFrame, in memory.

No server. No connection string. No CREATE TABLE. No file on disk. DuckDB is a SQL engine you imported, not a database you connected to.

The table name in the query is the Python variable name. Rename the variable and the query breaks: Table with name customers does not exist.

.df() on the end converts the answer back into a DataFrame. Without it you get a DuckDB relation — prints nicely, but has no .groupby() or .iloc.

Everything you write is real, portable SQL. The same text runs against Postgres, Snowflake or BigQuery — with the table names pointing at real tables instead of your notebook's variables.

2  •  Joins, and the Cardinality Trap

The section this chapter exists for.

Join Anatomy — Four Pieces, One Line

FROM customers c LEFT JOIN region_targets t ON c.region = t.region

is exactly customers.merge(region_targets, on="region", how="left")

customers c — alias. A nickname for the table, declared just by writing it. Now you say c.revenue. Pure convenience — until two tables share a column name, which is exactly what a join key is.

LEFT JOIN region_targets t — the second table, aliased t.

ON c.region = t.region — the join key. The column that must match for two rows to be glued together. Name the wrong column and you get a wrong answer, not an error.

First, a Join That Cannot Multiply Anything

FROM customers c LEFT JOIN region_targets t ON c.region = t.region

Four rows in, four rows out. region_targets has exactly one row per region, so nothing was duplicated. Hold on to that sentence.

LEFT — keep every left row even with no match, filling the right side with NULL, SQL’s mark for a missing value. That is how="left". Plain JOIN keeps only matched rows. If region_targets had no West row, LEFT JOIN would keep customers 1 and 3 with target NULL; plain JOIN would return only 0 and 2.

The Four Join Types — Read the Right-Hand Column

TypeKeepsRow count
INNER JOINOnly rows matching in both tablesCan shrink or grow
LEFT JOINAll left rows; NULL where no match≥ left table's rows
RIGHT JOINAll right rows; NULL on the left where no match≥ right table's rows
FULL OUTER JOINEverything from both; NULL on whichever side is missing≥ both

Almost everyone believes a LEFT JOIN preserves the left table's row count. It preserves those rows as a minimum.

A LEFT JOIN from 1,000 customers to 5,000 orders returns 5,000 rows, plus one for each customer with no orders — anywhere from 5,000 to 5,999, depending on the cardinality of the relationship. That is a fact about your data, not about your query.

Key Concept: A Join Has a Grain, and You Must Know It

The grain of a table is what one row represents: one customer, one customer-month, one order, one country-year.

Every join either preserves the grain or changes it. The habit is two sentences and one COUNT(*):

Before you write it. State the grain of both inputs and the grain you intend the output to have.

After you run it. Check the row count against that intention.

This single habit prevents the most consequential class of silent data error in applied work.

Poll: Predict the Row Count

customers has 600 rows, one per customer. orders has 4,033 rows — every customer placed between 1 and 12 orders.

SELECT c.customer_id, c.region, c.revenue
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id

How many rows come back?

A) 600 — a LEFT JOIN keeps the left table's rows
B) 4,033 — one row per order
C) 4,633 — both tables stacked together
D) 2,419,800 — every customer against every order

Answer: B — 4,033 Rows

Every customer appears once per order, with their revenue repeated verbatim each time.

A is the tempting wrong answer and usually wins the room. LEFT JOIN guarantees the left rows survive — not that they stay unique. D is what a CROSS JOIN gives you: every customer paired with every order.

The Poll’s Join, Drawn Out

SELECT c.customer_id, c.region, c.revenue
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id

Every order finds its customer, so the result has one row per order: 6 orders here, 4,033 in the poll (B). Customer 3 now appears three times with the same revenue. A, 600, is the customers table alone. C, 4,633, stacks the tables (600 + 4,033). D, 2,419,800, pairs every customer with every order (600 × 4,033).

Fanout — and Nothing Warned You

Revenue repeated 7 times, verbatim. Across the table: 600 rows → 4,033 rows, 6.72 per customer.

The join did exactly what you asked. The bug is in what you do next: compute a statistic as though each row were an independent customer.

It is invisible. The IDs are real, the revenue is real; no error, no warning. The only symptom is more rows than there should be, and nobody counts rows.

The Same Chapter 8 Test, Run Twice

Welch’s $t$-test: mean revenue per customer, East vs West, in dollars.

Correct (1 row/cust)   n =   600   diff = 11.31   SE = 9.35   t = 1.21   p = 0.2270
Fanned out (1/order)   n = 4,033   diff = 12.30   SE = 3.57   t = 3.44   p = 0.0006

Nothing Went Wrong. That Is the Problem.

$\text{SE} \propto \sigma/\sqrt{n}$

In words: the standard error divides by the square root of the sample size. Multiply the rows by 6.72 and the SE shrinks by $\sqrt{6.72} \approx 2.6$ — here 9.35 → 3.57, a factor of 2.62.

$t = \bar{d} \,/\, \text{SE}$

In words: the $t$-statistic is the difference divided by the standard error. The difference barely moved, 11.31 to 12.30. The denominator shrank. So $t$ inflated on its own.

The $t$-test did nothing wrong. The SE formula did nothing wrong. $n$ was wrong.

 And this is one of the errors the benchmark audit in the hook found in its answer key — the one-to-many join that is never re-aggregated.

The Fix: Aggregate Before You Join

A common table expression (CTE) names an in-between table, like saving a groupby result to a variable in pandas.

WITH order_counts AS (
    SELECT customer_id, COUNT(*) AS n_orders
    FROM orders
    GROUP BY customer_id
)
SELECT c.customer_id, c.region, c.revenue, oc.n_orders
FROM customers c
LEFT JOIN order_counts oc ON c.customer_id = oc.customer_id

1. The WITH block collapses orders to one row per customer and names it order_counts: 4,033 → 600.

2. The join meets exactly one order_counts row per customer, 1 : 1, so 600 in, 600 out.

The grain holds by construction, not by luck. Lost? Read it bottom up: the final query needs one row per customer, and the block above makes it.

Common Misconception

“SELECT DISTINCT fixes duplicate rows.”

It removes them from your output while leaving the cause in place — and it hides information.

If two of a customer's rows differ in any column — an order date, an order ID — DISTINCT keeps both. You still have fanout.

And when it does collapse rows, it removes the evidence that anything went wrong.

Diagnose the cardinality. Do not paper over it.

3  •  Aggregating Without Collapsing

The single highest-value piece of SQL for an economist.

GROUP BY Collapses. Sometimes You Need It Not To.

A panel of countries and years. GDP growth needs last year’s GDP on every row, within country: keep every row and add a column. GROUP BY cannot do that.

df.groupby("country")["gdp"].mean()
df["prev_gdp"] = df.groupby("country")["gdp"].shift(1)

The Same Idea, Term by Term

df.groupby("country")["gdp"].shift(1)

LAG(gdp) OVER (PARTITION BY country ORDER BY year)

OVER (...) is what turns an ordinary aggregate into a window function. SUM, AVG, COUNT, MIN, MAX all take it. Rows in, same rows out, extra columns.

PARTITION BY country is groupby("country"). Omit it and the window is the entire table.

ORDER BY year inside the OVER (...) tells the database what “previous” means. Pandas takes this from the DataFrame's row order — a source of hidden bugs. SQL lets you say it, and you should: leave ORDER BY out and “previous” follows whatever order the rows happen to be in, with no error.

That inner ORDER BY is unrelated to the query's own ORDER BY at the bottom, which only controls how the output prints.

The Window Functions Worth Knowing

FunctionDoespandas analogue
LAG(x, k)Value $k$ rows back within the partitiongroupby().shift(k)
LEAD(x, k)Value $k$ rows forwardgroupby().shift(-k)
ROW_NUMBER()1, 2, 3 … within partition; never tiesgroupby().cumcount() + 1
RANK() / DENSE_RANK()Rank, with / without gaps after tiesgroupby().rank()
SUM(x) OVER (...)Running totalgroupby().cumsum()
AVG(x) OVER (...)Group mean attached to every rowgroupby().transform('mean')

On ties: RANK() gives the same number then skips (1, 2, 2, 4). DENSE_RANK() ties without skipping (1, 2, 2, 3). ROW_NUMBER() never ties and breaks them arbitrarily (1, 2, 3, 4).

Chapter 2, Recomputed in SQL

WITH real_wages AS (
    SELECT year, nominal_wage,
           nominal_wage * (255.66 / cpi) AS real_wage_2019
    FROM wages
)
SELECT year,
       ROUND(nominal_wage, 2)   AS nominal,
       ROUND(real_wage_2019, 2) AS real_2019,
       ROUND(100.0 * (real_wage_2019
             / LAG(real_wage_2019) OVER (ORDER BY year) - 1), 2) AS growth_pct
FROM real_wages
ORDER BY year

The WITH block: real = nominal × 255.66 / CPI. 255.66 is the 2019 CPI, so the column is in 2019 dollars.

LAG brings last year’s real wage onto this year’s row, so growth = this year / last year − 1. 2019 has no earlier row: NULL.

Nominal wages rose every single year — \$23.51 to \$29.87, a gain of 27%.

Poll: What Does LAG Give the First Row?

In the query you just saw, LAG(real_wage_2019) OVER (ORDER BY year) for 2019 — the earliest year in the table — returns what?

A) 0
B) The 2020 value, wrapping around
C) NULL — there is no prior row, so there is no answer
D) An error, because the window is incomplete

Answer: C — NULL, and That Is a Feature

There is no earlier row in the partition, so LAG has nothing to return and says so. This propagates — the 2019 growth rate is NULL too. Pandas does the same thing when shift(1) produces NaN in the first row of each group.

Why A is the dangerous wrong answer: if LAG returned 0, the 2019 growth rate would compute as an infinite jump from nothing — and it would be a number rather than an obvious hole. NULL is SQL refusing to guess. That refusal is the subject of the next section.

Think Like an Economist: Provenance

Lars Vilhuber, the American Economic Association's Data Editor, has written about why computational reproducibility in economics fails. A recurring cause is not fraud or carelessness but provenance.

An analysis built on final_data_v3_USE_THIS.csv sitting on one laptop, produced by cleaning steps nobody wrote down.

A query against a versioned, immutable source is different in kind: the transformation is the code, the code is in git, and anyone can re-run it against the same bytes.

If you were hit by a bus, could a colleague reproduce your headline number from your repository alone? If the answer involves a file on your Desktop, you have a provenance problem.

4  •  NULL Is Not a Value

Defensible, standard, and responsible for more undetected errors than any other feature of the language.

Three Truth Values, Not Two

In Python

None == None

True

In SQL

NULL = NULL

NULL

The reasoning is sound. NULL means unknown, and two unknowns are not necessarily the same unknown. Asking whether one unknown equals another correctly returns “unknown”.

So SQL has three truth values, and a WHERE clause keeps only rows where the condition is true:

That last branch is where the money goes missing.

Poll: The Filter That Eats Your Data

An orders table has 8 rows. Exactly 2 have status = 'cancelled'. Two others have status = NULL — nobody recorded it.

SELECT COUNT(*) FROM orders WHERE status != 'cancelled'

How many rows come back?

A) 8 — nothing was excluded
B) 6 — the two cancelled orders were removed
C) 4 — both the cancelled and the unknown-status rows are dropped
D) 2 — only the cancelled rows survive

Answer: C — 4 Rows, and \$300 Gone

NULL != 'cancelled' evaluates to unknown, not true — and WHERE keeps only true. The two unknown-status rows were dropped.

They took \$300 of revenue with them: the query meant to keep \$1,000 and kept \$700, so 30% is gone, from a query whose author believed they were excluding cancellations. No error. No warning. The next slide shows the eight rows.

The Denominator That Changes Without Telling You

SELECT
  AVG(revenue)            AS avg_skips_nulls,
  SUM(revenue)/COUNT(*)   AS avg_over_all_rows
FROM orders

 avg_skips_nulls | avg_over_all_rows
-----------------+-------------------
       160.71    |      140.63

COUNT(*) counts rows. COUNT(column) counts non-null values in that column. Two different questions, one keystroke apart.

AVG ignores nulls, so it divides by 7. The same sum over all 8 rows gives 140.63. A 14% difference from nothing but a disagreement about the denominator.

And neither number is wrong. They answer different questions: “average revenue among orders where we know the revenue” and “average revenue per order.”

Common Misconception

“Missing values show up as zeros or NaN, so I'll notice them.”

NULL is not zero and is not NaN. It is absent from arithmetic entirely. It does not shift a sum. It does not appear as an outlier. It does not raise an error.

It removes rows from filters and shrinks denominators in aggregates — and both happen without a warning.

Before trusting any aggregate: run COUNT(*) alongside COUNT(column) for every column you aggregate. If they differ, you have a decision to make — and making it deliberately is the whole job.

Parquet: Storing by Column, Skipping What You Don't Need

1. Projection pushdown. Each column is its own block, so ask for two columns and the engine reads two: 2 of 6 here, 2 of 19 in the taxi file.

2. Predicate pushdown. If the file stores each chunk’s min and max, WHERE year = 2024 skips a chunk that holds only 2019, without reading it. The taxi file stores none, so there only step 1 helps.

The Pattern to Internalise

Do the heavy work where the data is.
Bring back only the small result.

Filter, join and aggregate in SQL until the output is small. .df() is the boundary between the two worlds; calling it as late as possible is most of what “working with large data” means.

Misconception: “you need Spark (a cluster of machines) for data bigger than RAM.” An engine that reads only the columns and rows a query needs streams through files far larger than memory. Reach for a cluster when you have measured that you need one.

Reading a Query You Did Not Write

You will read far more SQL than you write — from a colleague, a predecessor who has left, a dashboard nobody has audited in two years, or a language model. Six checks, index-card length.

1. Check the grain. COUNT(*) against COUNT(DISTINCT key). If they differ, you have fanout.

2. Check the row count against expectation. State what you expect first. “About 600 customers” is testable; “some rows” is not.

3. Check the joins. Is the right-hand table unique on the join key? If not, the join multiplies.

4. Check the filters against NULL. != 'cancelled' drops every NULL row — 30% of revenue in eight rows.

5. Check what it does not return. A customer dropped by an INNER that should have been LEFT; a month missing from a series, shifting every growth rate.

6. Compute one number by hand. Take one customer, work out their value, confirm the query agrees.

Check 5 is the failure mode most likely to survive review — because everything the query does return is correct.

A tiny example: customer A (revenue 100, 1 order) and customer B (revenue 400, 3 orders), both East. After the join, B appears three times.

customerregionc.revenueo.order_value

Illustrative numbers.

COUNT(DISTINCT c.customer_id) = 2. Right: duplicates are counted once.

SUM(o.order_value) = 30 + 50 + 70 + 80 = 230. Right: order value lives at the order grain, one row per order.

AVG(c.revenue) = (100 + 400 + 400 + 400) / 4 = 325. Wrong: the average per customer is (100 + 400) / 2 = 250. B counts three times.

WITH o AS (SELECT customer_id, SUM(order_value) AS total FROM orders GROUP BY customer_id)
SELECT c.region, COUNT(*) AS customers, AVG(c.revenue) AS avg_revenue, SUM(o.total) AS total_orders
FROM customers c LEFT JOIN o ON c.customer_id = o.customer_id
GROUP BY c.region

The fix: aggregate orders to one row per customer first; then all three numbers are right. A correct count beside a corrupted average looks consistent, and this query would pass code review at most companies.

Three Practices That Make LLM SQL Safe

1. Give it the schema, not just the question. Most made-up joins come from a model guessing at column names and how the tables relate. Paste the DESCRIBE output for every table involved.

2. Ask it to state the grain. “What does one row of your result represent?” If the answer is wrong, or missing, check every join.

3. Verify on a subset with a known answer. Ten hand-checked customers is enough: fanout and NULL bugs both show up at small scale.

The tool is fast and unreliable, so your job shifts from writing the query to checking it. Deciding whether an answer is correct has always been the harder and more valuable half.

Chapter 11 in a Nutshell

SQL and pandas implement the same relational algebra (Codd 1970). SQL is declarative — which is why its clauses execute in a different order than they are written.

There is no database. DuckDB resolves the table name out of your Python namespace, and .df() is the boundary back to pandas.

A join can multiply rows without warning. Because every SE depends on $n$, a fanned-out join turns a null result into a significant one without changing a single underlying fact. Aggregate to the grain you want before you join.

Window functions aggregate without collapsing: LAG over a partition is groupby().shift(), and it is how you get growth rates, ranks and running totals on panels.

NULL is unknown, not zero. It removes rows from filters and shrinks denominators in aggregates — without warning, in both directions.

Columnar formats with pushdown let you query files far larger than memory. Do the heavy work where the data is; bring back the small result.

You will read more SQL than you write, much of it machine-generated. Check the grain, the row count, the join cardinality, the NULL handling — and verify one number by hand.
